# VOIDLINE — Technical Architecture

## Current scene
Assets/VOIDLINE/Scenes/main.unity is the only enabled build scene. The static scene contains the camera, lighting, GameManager, player craft, and CorridorRoot with three one-time intro segments. Runtime-created objects include the HUD, EventSystem, hazards, and pickups.

## Runtime responsibilities
- **VoidlineBootstrap** — ensures a game manager exists when the main scene loads.
- **VoidlineGameManager** — coordinates the run lifecycle, score/hull rules, spawning, object pools, and current prototype HUD. It is an orchestrator, not the preferred home for future standalone systems.
- **VoidlinePlayerController** — owns movement limits and banking; consumes Player/Move from the Input System action asset.
- **VoidlineAsteroid** — reusable moving hazard; resolves one collision or pass and returns itself to the manager's pool.
- **VoidlinePickup** — reusable repair collectible; owns bobbing/rotation and delegates reward/pooling to the manager.
- **VoidlineRunSettings** — designer-facing ScriptableObject for world speed, hull, spawn pacing, lane bounds, pickup cadence, and pickup score.
- **VoidlineAudioFeedback** — synthesizes short one-shot clips at runtime and plays feedback for hits, passes, pickups, UI, and run end.
- **VoidlineCameraEffects** — decaying trauma shake applied to the camera only; never moves gameplay colliders.
- **CorridorScroller** — scrolls the three-piece opening corridor once, then retires each segment behind the camera; it does not loop those same pieces back into view.
- **VoidlineRouteDirector** — generates the one seeded curved centerline used by the player, scrolling scenery, hazards, pickups and landmarks. Parallel route/fork logic is explicitly de-scoped.

## Extension rules
1. Add new tuning values to VoidlineRunSettings; avoid scattering unexplained magic numbers across scripts.
2. Put behavior in a focused component and let the manager coordinate it. Avoid adding unrelated systems to VoidlineGameManager.
3. Add new controls to InputSystem_Actions.inputactions and consume actions rather than adding more keyboard-only polling.
4. Use prefabs for reusable scene actors and simple colliders for gameplay. Keep visual meshes separate from collision shapes.
5. Return temporary actors to pools; reset all per-run state in Configure.
6. Keep camera effects cosmetic and unscaled-time-driven so pause/game-over states do not leave the camera offset.
7. Save the scene after editor-time changes. Do not save runtime state from Play Mode.
8. Do not overwrite existing third-party source assets. Create project-owned prefabs/materials under Assets/VOIDLINE.
9. After external asset or script edits, refresh/recompile, inspect Console, then run Play Mode checks.
10. Before committing, inspect git status and preserve user changes. Never reset the working tree as a cleanup shortcut.

## Known prototype debt
- HUD and EventSystem are generated by VoidlineGameManager; a later UI phase should extract them into prefab-backed components.
- Audio uses synthesized one-shots on one source; a future audio phase can add an AudioMixer with Master/SFX/Ambience buses and user volume controls.
- High score uses PlayerPrefs; adequate for one local best-score value, not a full save-slot/progression system.
- Camera remains fixed; avoid adding camera follow unless it improves the intended corridor framing.
- Build artifact and standalone runtime verification remain separate from Editor Play Mode QA.
